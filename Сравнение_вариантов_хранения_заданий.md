# Домашнее задание 13 — наследование таблиц и EAV

Предметная область: персонализированное обучение RemI AI. Сущность — диагностическое задание. Рассмотрены два предусмотренных ТЗ типа: числовой ответ и короткий текстовый ответ. Это учебное сравнение четырёх альтернатив, а не утверждённая производственная схема. Простой учебный формат применён, поскольку конкретный стандарт оформления не задан.

## Поля сущности

Общие поля: question_id — технический идентификатор, prompt — текст задания. Числовой тип имеет expected_number (ожидаемое число) и tolerance (неотрицательный абсолютный допуск). Текстовый тип имеет evaluation_rubric — критерии оценивания короткого ответа. Критерии позволяют оценивать ответ по смыслу в рамках рубрики; наличие поля не означает, что реализован автоматический оценщик.

Идентификатор и конкретные имена полей — технический выбор для упражнения. Ожидаемый ответ и рубрика нужны для проверки задания. Числовой допуск — предложенный учебный способ учитывать точность ответа, а не утверждённое требование ТЗ. При допуске 0 требуется точное совпадение; правило проверки |ответ − ожидаемое число| ≤ tolerance реализуется отдельно.

Задания с выбором ответа тоже предусмотрены ТЗ, но не включены в сравнение, потому что домашка просит ровно два типа. Поля модерации, проверки генерации и связей с компетенциями потребуются полноценной системе; здесь показана только структура выбранной сущности.

## 1. Single Table Inheritance

Схема hw13_sti содержит одну таблицу question. Тип задаётся answer_type. Для числового задания заполняются ожидаемое число и допуск, для текстового — рубрика. CHECK проверяет допустимый набор заполненных полей, включая отсутствие полей другого типа. Это иллюстрирует, что в данном простом случае часть ограничений можно обеспечить самой базой.

Плюс: вся запись извлекается из одной таблицы. Минус: поля другого типа остаются NULL, а при увеличении числа типов таблица и проверки усложняются.

## 2. Class Table Inheritance

В условии написано Common Table Inheritance, в лекции — Class Table Inheritance. Используем описанную в лекции модель: общая question и две дочерние таблицы numeric_question и short_text_question в hw13_class. Их первичные ключи одновременно ссылаются на родительскую запись.

Общие данные хранятся один раз, специфичные поля имеют конкретные типы и NOT NULL. Для полного объекта нужен JOIN. Вставка родителя и подтипа должна выполняться одной транзакцией.

Важное ограничение учебной реализации: внешние ключи гарантируют существование родителя, но не гарантируют ровно один подтип. Возможны родитель без подтипа или запись сразу в обоих подтипах. Приложение должно проверять это правило; более строгие механизмы выходят за показанную простую схему.

## 3. Concrete Table Inheritance

В hw13_concrete две самостоятельные таблицы без родителя. Каждая содержит question_id и prompt, а также свои поля ответа. Для чтения одного типа не нужен JOIN. Общая структура дублируется, поэтому добавление общего поля требует изменения двух таблиц.

Идентификаторы уникальны только внутри соответствующей таблицы: номер 1 может быть и у числового, и у текстового задания. Для общего списка следует учитывать тип вместе с идентификатором. Общая ссылка из истории ответов на любой тип усложняется, что снижает удобство этой модели для RemI AI.

## 4. Entity Attribute Value

В hw13_eav таблица question хранит стабильные основные поля и тип; attribute — определения расширяемых характеристик; question_value — значения характеристик конкретного задания. Составной первичный ключ запрещает два значения одной характеристики для одного задания.

Для числового типа предполагаются атрибуты expected_number и tolerance, для текстового — evaluation_rubric. Их можно добавлять записями без изменения структуры таблиц. CREATE TABLE создаёт структуру, но не наполняет словарь атрибутов.

Значения хранятся как TEXT. Значит, база не проверяет, что tolerance является числом и неотрицателен, а также что каждому типу заданий заданы все обязательные характеристики. Валидация типов, набора атрибутов и обязательности требуется в приложении. Например, строка «abc» формально поместится в значение tolerance, хотя предметно недопустима. Это сознательное ограничение простого EAV из лекции, а не преимущество перед типизированными колонками.

## Выбор для проекта

Для дальнейшего рассмотрения предлагается Class Table Inheritance: в ТЗ набор форматов ответа фиксирован, общие данные задания нужны диагностике и истории, а специфичные поля имеют разные типы. Перед использованием необходимо решить вопрос гарантии ровно одного подтипа. Для небольшого числа простых типов STI тоже является разумным вариантом и позволяет выразить ограничения в CHECK.

EAV представлен для выполнения задания: потребность в произвольных пользовательских характеристиках текущим ТЗ не установлена. Data Vault в домашке не требуется.

## Как выполнить

Открыть Query Tool именно базы, созданной пользователем для RemI AI, и проверить SELECT current_database(). Фактическое имя базы может отличаться регистром от написанного пользователем. Затем открыть «Домашнее задание 13.sql» и выполнить целиком. SQL содержит BEGIN/COMMIT: при ошибке следует сначала изучить её причину и состояние транзакции.

Скрипт создаёт четыре новые схемы: hw13_sti, hw13_class, hw13_concrete и hw13_eav, всего девять таблиц (1 + 3 + 2 + 3). Повторный запуск при существующих схемах завершится ошибкой; удалять их автоматически не предусмотрено. PostgreSQL INHERITS не используется: показаны способы моделирования из лекции.
