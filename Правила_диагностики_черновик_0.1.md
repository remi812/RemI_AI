# RemI AI: правила диагностики — рабочий черновик 0.1

## Статус

Это предложение для MVP, а не проверенная методика оценки знаний. Конкретные пороги, порядок обхода графа и лимиты являются гипотезами для обсуждения с преподавателем и проверки на практике. Документ описывает будущую логику; автоматически в приложении она ещё не реализована.

## 1. Начало диагностики

Студент выбирает дисциплину или конкретную тему. Для выбранной цели заранее задаётся список ключевых компетенций, которые необходимо проверить. Для темы диагностический движок начинает с одной из её ключевых компетенций; для дисциплины — с одной из ключевых компетенций дисциплины. Если назначено несколько ключевых компетенций, первую выбираем по заранее заданному порядку, чтобы поведение было воспроизводимым.

Каждый вопрос проверяет определённую компетенцию. Реальному студенту показываются только задания, прошедшие предусмотренную проверку. Генерация ИИ не равна проверке: при неудачной проверке система берёт резервный подтверждённый вопрос. Если подходящего подтверждённого вопроса нет, система прекращает проверку этой компетенции, сохраняет неопределённость и сообщает причину.

В базе сейчас учебные вопросы ожидают проверки; до появления проверенного набора проводить настоящую диагностику по этим данным нельзя.

## 2. Проверка одной компетенции

Предварительная гипотеза для первой версии:

1. Задавать разные вопросы по одной компетенции, не повторяя один и тот же вопрос в пределах этой проверки.
2. После первого ответа итоговый вывод не делать.
3. Если из двух проверенных и оценённых ответов оба правильные — считать компетенцию предварительно освоенной.
4. Если оба неправильные — считать её вероятным пробелом.
5. Если один правильный и один неправильный — задать третий проверенный вопрос. При двух правильных из трёх считать компетенцию предварительно освоенной; при двух неправильных — вероятным пробелом.
6. Если необходимых проверенных вопросов или подтверждённых оценок не хватило, либо достигнут лимит сессии — оставить статус «требуется уточнение». Если ни одного оценённого ответа нет — «не оценено».

Эти правила описывают только учебную гипотезу. Два правильных ответа не доказывают полного владения темой, а два неправильных не объясняют причину ошибки. Задания должны проверять соответствующий навык и быть достаточно разнообразными. Результат не используется как официальная аттестация.

Открытый короткий ответ учитывается только после оценки по определённым критериям и, если это необходимо, экспертной проверки. Ответ с неподтверждённой оценкой не считается ни правильным, ни неправильным.

## 3. Проверка предварительных знаний

Если компетенция получила статус «вероятный пробел», система находит её непосредственные предпосылки по графу и выбирает одну для проверки. Если предпосылок несколько, в первой версии используется явно заданный порядок; затем можно использовать приоритет из концепции проекта после его проверки.

Если проверенная предпосылка тоже оказалась вероятным пробелом, система может перейти к её предпосылкам. Если она предварительно освоена, система не включает её в обязательное повторение на основании этой проверки. Когда данные недостаточны, предпосылка остаётся неопределённой, а причина ошибок не объявляется установленной.

После проверки доступных предпосылок система возвращается к оставшимся ключевым компетенциям выбранной цели. Рекомендуемый порядок связей и содержательная корректность графа требуют проверки преподавателем. Временный предел углубления — три ребра от исходной компетенции; если он достигнут, более глубокие предпосылки остаются не оценёнными.

## 4. Окончание сессии

Предварительный лимит — до 20 показанных заданий на одну сессию. Диагностика заканчивается раньше, если для запланированных ключевых компетенций собраны данные и проверены доступные предпосылки, либо продолжить невозможно из-за отсутствия проверенных заданий.

В результатах необходимо указать, почему диагностика завершилась: достаточно данных по запланированным проверкам, достигнут лимит, не хватило заданий или студент остановил сессию. Незавершённые и непроверенные компетенции сохраняются как требующие уточнения или не оценённые. Лимит и глубина — гипотезы из концепции, а не подтверждённые оптимальные значения.

## 5. Карта, уверенность и маршрут

На карте показываются предварительно освоенные компетенции, вероятные пробелы, непроверенные узлы и те, где требуется уточнение. Оценка освоения и достаточность свидетельств хранятся отдельно. До согласования способа расчёта числовые показатели остаются пустыми; нельзя выдавать их за научно обоснованные проценты.

Маршрут формируется по проверенным связям: сначала базовые вероятные пробелы, затем более сложные темы на пути к выбранной цели. Неоценённая предпосылка обозначается отдельно: система может предложить её проверить, но не выдаёт её за установленный пробел. Предварительно освоенные компетенции не включаются в обязательное повторение без новых оснований.

Для каждого шага показываются объяснение и подходящие материалы из каталога. Рекомендуются только материалы, допущенные модератором и доступные по актуальной ссылке; язык и условия доступа учитываются при выборе. Если подтверждённого материала нет, система прямо сообщает об этом, не придумывая курс. После изучения студент может пройти повторную проверку, а история прежних результатов сохраняется.

## 6. Разбор на существующих учебных сценариях

В базе есть два вымышленных студента с целью «Объяснять обратную связь». Их ответы и маршруты составлены вручную, а вопросы пока не прошли модерацию. Поэтому примеры показывают предполагаемый ход алгоритма, но не доказывают его работу.

| Студент | Учебные ответы | Предварительное поведение будущего алгоритма |
| --- | --- | --- |
| А | Два неверных ответа по вычислению значения функции. | Если вопросы и их оценка подтверждены, правила выше обозначат вероятный пробел по вычислению функции. Для связи этого пробела с целью нужно пройти проверку промежуточных компетенций; причина ошибки по ТАУ заранее не установлена. |
| Б | Два неверных ответа об обратной связи. | Если вопросы и оценка подтверждены, правила обозначат вероятный пробел по обратной связи. Затем система проверит одну из её предварительных компетенций по графу. |

Текущие сохранённые оценки обоих студентов имеют статус `needs_review` и не меняются автоматически этим документом. Их существующие маршруты демонстрационные; у студента А промежуточные результаты проверки пока отсутствуют, поэтому нельзя считать маршрут подтверждённым результатом нового алгоритма.

## 7. Что согласовать перед реализацией

- Подходят ли ориентировочные правила двух-трёх вопросов на компетенцию и как подобрать задания разной сложности?
- Как выбирать стартовые ключевые компетенции и какой порядок предпосылок задавать для каждой цели?
- Как вычислять отдельные показатели освоения и уверенности, либо оставить только текстовые статусы?
- Как применять лимит в 20 вопросов и глубину три, если пользователь хочет продолжить диагностику позже?
- Кто утверждает вопросы, связи и ресурсы; как часто проверять доступность курсов?
- Как оценивать короткие ответы и фиксировать версию критериев и генератора?
